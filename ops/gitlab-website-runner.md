# Projekt-Runner für die White-Gloss-Website

GitLab führt die fünf Website-Prüfungen auf einem projektgebundenen Linux-Runner aus. Ein eigenes Dienstkonto auf dem vorhandenen VPS betreibt dazu eine Rootless-Podman-Instanz. Der Manager nutzt deren lokalen Socket. In die Job- und Service-Container wird kein Host-Socket eingebunden. Es läuft jeweils ein Job. Der Runner begrenzt den Buildcontainer auf zwei CPU-Kerne und 4 GiB RAM sowie einen optionalen Service auf einen Kern und 768 MiB. Die Betriebsreserve für Website und GitLab vor dem ersten großen Build prüfen.

Der einmalige Einrichtungsweg auf dem Hostinger-VPS ist `python3 -I ops/bootstrap-gitlab-website-runner.py` aus dem geprüften Website-Commit. Bestätige den im Terminal angezeigten Gerätecode in deinem GitLab. Der Helfer verknüpft den Runner mit dem privaten Website-Projekt, setzt die drei Testvariablen und aktiviert den Runner. Bei einer Unterbrechung kann derselbe Befehl erneut ausgeführt werden. Für eine manuelle Einrichtung gelten die folgenden Schritte.

Ist der Projekt-Runner bereits angelegt und pausiert, kann die lokale Einrichtung mit `python3 -I ops/bootstrap-gitlab-website-runner.py --resume-local PROJEKT_ID RUNNER_ID` fortgesetzt werden. Verwende die beiden numerischen IDs aus GitLab. Der Helfer prüft die geschützte Vormerkung auf dem VPS, startet den Manager und ersetzt die Vormerkung durch eine Bestätigung ohne Zugangsdaten. Anschließend die drei Projektvariablen prüfen, den Runner in GitLab freigeben und einen Testjob ausführen.

Für Checkout und Artefakt-Upload erreichen die Job- und Hilfscontainer das GitLab auf demselben VPS über `gitlab-p1va.srv2077393.hstgr.cloud:host-gateway` in `runners.docker.extra_hosts`. Ein erneuter Installer-Aufruf mit derselben Runner-ID ergänzt diesen Eintrag bei bestehenden Installationen. Die HTTPS-Adresse und Zertifikatsprüfung gelten auch im Container.

1. Im **privaten Website-Projekt** unter **Settings › CI/CD › Runners › Create project runner** einen Projekt-Runner anlegen. Tag `white-gloss-website` setzen, ungetaggte Jobs ausschalten, an dieses Projekt binden. Er muss interne Merge Requests ausführen dürfen. Das geht auch mit `POST /api/v4/user/runners`, `runner_type=project_type`, der numerischen `project_id`, `tag_list=white-gloss-website`, `locked=true`, `run_untagged=false` und `access_level=not_protected` mit einem entsprechend berechtigten `create_runner`-Zugang. Der Runner-Token `glrt-…` wird bei der Erstellung einmal angezeigt.
2. Die Datei `ops/install-gitlab-website-runner.sh` aus dem geprüften Commit in der Hostinger-Konsole als root mit der von GitLab vergebenen Runner-ID aufrufen. Beispiel für ID 12: `bash ops/install-gitlab-website-runner.sh 12`. Den Token erst in die verdeckte Eingabe der Konsole einsetzen. Für eine lokale Installation aus einem geschützten Dateideskriptor unterstützt der Helfer `--token-stdin`. Der Helfer lädt die festgelegte Version des GitLab Runners, prüft deren SHA-256 und testet die DNS-Auflösung zwischen zwei temporären Containern im eigenen Netzwerk. Ein wiederholter Aufruf mit derselben ID überprüft die vorhandene Registrierung.
3. Im Website-Projekt die nicht geheimen CI-Variablen `WHITE_GLOSS_GITLAB_RUNNER_ID` und `WHITE_GLOSS_GITLAB_PROJECT_ID` auf die von GitLab bestätigten IDs setzen. `WEBSITE_ISOLATED_FLOWTESTS_ENABLED=true` nur für die isoliert konfigurierte Website-CI einschalten. Diese Steuerwerte müssen den internen MR-Jobs zur Verfügung stehen. Produktionszugangsdaten separat an die geschützte Veröffentlichung binden.
4. Einen internen Merge Request prüfen. In GitLab müssen die Jobs dem neuen Runner zugeordnet sein. Zuerst die Datenbankprüfung mit dem Alias `postgres`, dann die Build- und Browserprotokolle kontrollieren. Die Anmeldung des Dienstes allein bestätigt noch keinen erfolgreichen Build.

Auf diesem Ubuntu-VPS erwartet der Helfer systemd/cgroup v2, Podman ab 4.2 und Rootless-UID/GID-Mappings. Er ergänzt die fehlenden Ubuntu-Netzwerkpakete `passt` und `aardvark-dns` und prüft die Namensauflösung zwischen zwei Containern. GitLab empfiehlt für Podman neuere Aardvark-DNS-Versionen als 1.10.0. Einen geplanten Stopp in GitLab über **Pause** einleiten und laufende Jobs auslaufen lassen. Der dedizierte Dienst heißt `white-gloss-gitlab-runner.service`.

Meldet Podman beim Beenden des letzten Containers `rootless netns: kill network process: permission denied`, prüft `python3 -I ops/repair-gitlab-pasta-apparmor.py` im Rootterminal den bekannten Fehler unter Ubuntu 26.04. Bei bestätigter Verweigerung ergänzt der Helfer im systemweiten, vom Paket `passt` gelieferten Profil die Regel `signal (receive) set=(term) peer=podman,`. Er verwendet die lokale Ergänzungsdatei, falls das Paket sie einbindet, und lädt ausschließlich das Profil `pasta` im Erzwingungsmodus neu. Das erlaubt Podman auf diesem VPS, seine pasta-Prozesse per SIGTERM zu beenden.
